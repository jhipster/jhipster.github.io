## Introduction

JHipster comes with an extensive set of tests, and each generated application has:

* Unit tests using [JUnit 5](https://junit.org/junit5/).
* Integration tests using the Spring Test Context framework.
* UI tests with [Vitest](https://vitest.dev/).
* Architecture tests with [ArchUnit](https://www.archunit.org/).

Optionally, JHipster can also generate:

* Performance tests with [Gatling](http://gatling.io/).
* Behaviour-driven tests with [Cucumber](https://cucumber.io/).
* Angular/React/Vue integration tests with [Cypress](https://www.cypress.io/) or [Playwright](https://playwright.dev/).

We have two goals in generating those tests:

* Help every JHipster user to follow best practices, as we believe tests are a very useful part of every application
* Validate that what is being generated is correct. So even if you don't plan to use those tests at all, doing `npm run backend:unit:test` and `npm test` after generating your application is a good way of knowing if everything is fine. You are then free to ignore those tests if you think that testing is a waste of time!

The Java tests, the end-to-end tests, and the Gatling and Cucumber tests are generated in the standard Maven `src/test` folder. UI unit tests are located next to the code they test, in the `src/main/webapp` folder.


## Integration tests

Integration tests are done with the Spring Test Context framework, and are located in the `src/test/java` folder. JHipster will launch a specific Spring test context, which will be re-used along all tests, as:

* Your Spring beans should be stateless and thread-safe, and thus can be re-used across your different tests suites.
* Launching only one Spring context for all tests is a lot faster than launching a new Spring context for each test.

This Spring test context will use a specific test database to run its tests:

* If you use an SQL database, the tests use your development database: an in-memory H2 instance if H2 is your development database, otherwise a containerized version of it using [Testcontainers](https://www.testcontainers.org/modules/databases/). When the tests are run with the `prod` profile (`npm run backend:unit:test -- -Pprod`), which activates the `test,testprod` Spring profiles, JHipster will launch a containerized version of the production database using Testcontainers. Either way, Liquibase will be run automatically, and will generate the database schema.
* If you use Cassandra, JHipster will launch a containerized version of Cassandra with Docker using [Testcontainers](https://www.testcontainers.org).
* If you use MongoDB, JHipster will launch a containerized version of MongoDB with Docker using [Testcontainers](https://www.testcontainers.org).
* If you use Elasticsearch, JHipster will launch a containerized version of Elasticsearch with Docker using [Testcontainers](https://www.testcontainers.org).
* If you use Couchbase, JHipster will launch a containerized version of Couchbase with Docker using [Testcontainers](https://www.testcontainers.org).
* If you use Neo4j, JHipster will launch a containerized version of Neo4j with Docker using [Neo4j Testcontainers](https://www.testcontainers.org/modules/databases/neo4j/).

Those tests can be run directly in your IDE, by right-clicking on each test class, or by running `npm run backend:unit:test`.

**Limitations:** if the generated entities have validation enabled, JHipster is not enable to generate the correct values depending on the validation rules. Those rules can be so complex, for example if a Regex pattern is used, that this not possible. In this case, the tests will fail validation, and the default values used in the test will need to changed manually, so they can pass the validation rules.


## UI tests

UI tests come in two flavors with JHipster: unit tests with Vitest, and integration tests with Cypress or Playwright. Only Vitest is provided by default, but if you want to have a good test coverage of your application, we recommend that you use both tools together.

### Vitest

UI unit tests are the `*.spec.ts` files located next to the code they test, in the `src/main/webapp` folder. They use [Vitest](https://vitest.dev/).

Those tests will mock up the access to the application's REST endpoints, so you can test your UI layer without having to launch the Java back-end.

* Those tests can be run using `npm test`.
* Tip: if you want to focus on a single test change the module description from `describe('...', () => {` to `describe.only('...', () => {` and Vitest will run this test only.

### Cypress/Playwright

UI integration tests are done with [Cypress](https://www.cypress.io/) or [Playwright](https://playwright.dev/), and are located in the `src/test/javascript/cypress/e2e` or `src/test/javascript/playwright/e2e` folder.

Those tests will launch a Web browser and use the application like a real user would do, so you need to have a real application running, with its database set-up.

Those tests can be run using `npm run e2e`.


## Architecture tests

Architecture tests, which enforce certain constrainsts and best practices are done with [ArchUnit](https://www.archunit.org/).
You can write your own rules to check custom constraints for your architecture at build time following the [official documentation](https://www.archunit.org/userguide/html/000_Index.html).


## Performance tests

Performance tests are done with [Gatling](http://gatling.io/), and are located in the `src/test/java/gatling/simulations` folder. They are generated for each entity, and allow to test each of them with a lot of concurrent requests.

**Warning!** At the moment, those tests do not take into account the validation rules you may have enforced on your entities. Also tests for creating entities that have a required relationship with another entity will fail out of the box. You will anyway need to change those tests, according to your business rules, so here are few tips to improve your tests:

* On your running application, go to the `Administration > Logs` screen, and put `org.springframework` in `debug` mode. You will see the validation errors, for example.
* Use the application normally and open the Chrome `console log`: you will be able to see the REST requests with all their parameters, including the HTTP headers.

For running Gatling tests on a microservice application, you have to:

* Run a registry
* Run a gateway
* Run the microservice application
* Then, you can run Gatling tests

### Using Maven to run Gatling

You can execute all Gatling tests with `./mvnw gatling:test`.

### Using Gradle to run Gatling

You can execute all Gatling tests with `./gradlew gatlingRun`.


## Behaviour-driven development (BDD)

Behaviour-driven development (BDD) is available using [Cucumber](https://cucumber.io/), with its [JVM implementation](https://github.com/cucumber/cucumber-jvm).

[Gherkin](https://docs.cucumber.io/gherkin/reference/) features will have to be written in your `src/test/resources/<your_package>/cucumber` directory.
